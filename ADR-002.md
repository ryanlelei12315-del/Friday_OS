# ADR-002: Model Provider Abstraction

## Status
Proposed

## Context
FridayOS hardcodes Gemini (Realtime and Flash) inside its canonical entrypoints (`main.py` and `agent.py`). It also uses Groq Llama for background tasks and Ollama Llama for pyautogui. This binds Friday's logic directly to specific vendor SDKs, making it impossible to switch providers without rewriting the application.

## Problem
How do we isolate model interactions behind a unified interface, allowing providers (OpenAI, Anthropic, Google, local models) to be swapped out seamlessly?

## Options Considered
1. **Vendor SDKs (Option 1)**: Continue using native SDKs (Google AI, Groq client). High performance but hard-couples code to vendors.
2. **LangChain/LlamaIndex Abstractions (Option 2)**: Wrap all model calls in unified LangChain class interfaces. Easy to swap but introduces substantial dependency bloat.
3. **Unified Internal Model Router (Option 3)**: Write a lightweight internal Model Router interface defining clear abstractions for Text, Planning, Vision, and Streaming Voice model tasks.

## Decision
**Option 3: Unified Internal Model Router**. We will build an internal model abstraction layer. LLM interactions will register as Capabilities (e.g. `Router.get_strong_model()`), allowing vendors to be swapped seamlessly.

## Consequences
* **Positive**: Minimizes vendor lock-in, optimizes cost-to-performance by routing to cheaper models, and keeps dependencies clean.
* **Negative**: Requires writing custom adapter classes for each provider.

## Rejected Alternatives
* **Option 2 (LangChain)**: Rejected due to significant package bloat and instability across version updates.

## Future Revisit Conditions
Revisit if standard unified routing libraries (like LiteLLM) mature enough to replace custom internal adapters without adding bloated dependencies.
