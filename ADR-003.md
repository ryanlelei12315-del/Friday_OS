# ADR-003: Memory Architecture

## Status
Proposed

## Context
The current memory implementation is fragmented and uncoordinated across three separate backends: PostgreSQL (SQLAlchemy conversation logging), ChromaDB (long-term memory search), and Mem0 (unused local pgvector client). Mem0 crashes on import due to hardcoded localhost credentials.

## Problem
How can we build a stable, unified memory tier that coordinates short-term sessions, long-term facts, and procedural macro caching under standard credentials?

## Options Considered
1. **Single Postgres Database (Option 1)**: Move all memory (conversations and vector embeddings) to a single PostgreSQL database utilizing the `pgvector` extension.
2. **Dual-Tier SQLite + Local Vector (Option 2)**: Use SQLite for structured conversation history and ChromaDB for local vector embeddings, eliminating heavy Postgres network dependencies.
3. **Unified Memory Coordinator (Option 3)**: Keep PostgreSQL for relational logs and ChromaDB for local/RAG vector blocks, but coordinate them under a single lazy-loaded Memory Coordinator.

## Decision
**Option 3: Unified Memory Coordinator with Lazy-Loading**. We will maintain the Postgres and ChromaDB structures but isolate them behind a single, unified `MemoryCoordinator` that initializes database connections lazily, preventing import-time crashes.

## Consequences
* **Positive**: Resolves import-time database crashes, unifies retrieval queries under a single client, and maintains structured relational history.
* **Negative**: Requires maintaining two separate database systems (Postgres and ChromaDB).

## Rejected Alternatives
* **Option 2 (SQLite)**: Rejected because it does not support high-concurrency relational queries needed for web HUD dashboards.

## Future Revisit Conditions
Revisit if Postgres with pgvector becomes a single, unified local dependency, allowing us to drop ChromaDB entirely.
