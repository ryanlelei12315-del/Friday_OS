# ADR-004: Tool Architecture

## Status
Proposed

## Context
Existing tools are registered as direct, loose `@function_tool` decorated functions in `main.py`. They lack risk-level classifications, parameter validation schemas, timeout controls, cancellation handles, or standardized verification checks.

## Problem
How do we organize Friday's capabilities to ensure they are safe, predictable, validated, and non-blocking?

## Options Considered
1. **Raw Decorated Functions (Option 1)**: Keep the direct decorator registration pattern. Low complexity but offers zero security or validation boundaries.
2. **LangChain Tool Structures (Option 2)**: Rewrite all tools to use LangChain's `@tool` decorator. Integrates well with LangChain agents but is incompatible with LiveKit Realtime.
3. **Pydantic-Validated Class Registry (Option 3)**: Implement an abstract `FridayTool` class requiring strict input schemas, timeout controls, risk grading, and structured observations.

## Decision
**Option 3: Pydantic-Validated Class Registry**. All tools will inherit from the abstract `FridayTool` base class, enforcing standardized validation, security checks, and error logging boundaries.

## Consequences
* **Positive**: Guarantees parameters are validated before running, isolates secrets, enforces execution timeouts, and enables risk-based authorization.
* **Negative**: Requires rewriting existing decorated function tools into class definitions.

## Rejected Alternatives
* **Option 2 (LangChain Tools)**: Rejected because they do not map cleanly to LiveKit's native agent runtime tool definitions.

## Future Revisit Conditions
Revisit if the LiveKit Agents SDK natively supports Pydantic validation and timeout metadata within its `@function_tool` decorators.
