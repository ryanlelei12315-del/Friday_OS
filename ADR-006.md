# ADR-006: Model Context Protocol (MCP) Integration

## Status
Proposed

## Context
FridayOS contains a decoupled FastMCP server in `mcp/mcp/server.py` with duplicated main blocks and dead imports. This server is completely unused by the active LiveKit agent.

## Problem
How should FridayOS utilize the Model Context Protocol (MCP) without overcomplicating the system architecture?

## Options Considered
1. **MCP as the Core (Option 1)**: Rebuild the entire agent architecture around MCP, making Friday's core run as an MCP client interacting with local/remote MCP servers.
2. **Remove MCP (Option 2)**: Delete MCP components and stick purely to native LiveKit tools. Easy, but loses interoperability with external tools.
3. **MCP as a Tool Provider (Option 3)**: Keep MCP as a pluggable capability provider underneath the unified Tool Registry.

## Decision
**Option 3: MCP as a Tool Provider**. Friday Core will remain the primary orchestrator, but the Tool Registry will implement an MCP client adapter. This allows Friday to load standard MCP servers (like filesystem or search) as native tools.

## Consequences
* **Positive**: Preserves external tool interoperability, keeps Friday Core lightweight, and avoids locking the system to a single transport protocol.
* **Negative**: Requires maintaining an internal MCP client bridge.

## Rejected Alternatives
* **Option 1 (MCP as Core)**: Rejected because it overcomplicates local process execution and is incompatible with the real-time LiveKit streaming loop.

## Future Revisit Conditions
Revisit if the LiveKit Agents SDK natively supports MCP server mounting and tool schema conversions.
