# ADR-007: Device Architecture

## Status
Proposed

## Context
FridayOS is currently hardcoded as a single-host Windows application. It has no awareness of other user devices, such as mobile phones, tablets, or local smart-home deployment nodes.

## Problem
How can Friday coordinate actions across a user's multi-device ecosystem securely and efficiently?

## Options Considered
1. **MQTT Broker (Option 1)**: Deploy a centralized MQTT broker for device messaging. High performance, but adds a heavy, external local network dependency.
2. **REST API Polling (Option 2)**: Have companion devices poll Friday's core API periodically. High battery consumption and slow execution speeds.
3. **Encrypted Local WebSockets (Option 3)**: Deploy a secure, lightweight WebSocket server inside Friday Core, with devices connecting over local TLS.

## Decision
**Option 3: Encrypted Local WebSockets**. Friday Core will host a secure WebSocket server. Registered companion devices establish background connections, publishing their available capabilities to the central registry.

## Consequences
* **Positive**: Minimizes battery usage on mobile nodes, ensures low-latency execution, and keeps traffic entirely private within the local network.
* **Negative**: Requires handling local network IP changes and pairing handshakes.

## Rejected Alternatives
* **Option 2 (REST API Polling)**: Rejected due to unacceptable latency and high battery drainage on mobile nodes.

## Future Revisit Conditions
Revisit if we transition to cloud-assisted multi-device routing, which would require deploying a secure cloud broker.
