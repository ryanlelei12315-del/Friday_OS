# ADR-010: Observability and Tracing

## Status
Proposed

## Context
FridayOS currently prints raw text logs directly to stdout. There are no structured events, telemetry exports, tracing spans, or diagnostic alert systems, making debugging complex agent loops incredibly difficult.

## Problem
How do we monitor, trace, and debug Friday's internal decisions, tool executions, and state transitions?

## Options Considered
1. **Raw Log Files (Option 1)**: Output stdout logs to text files. Simple, but offers zero structural querying or trace capabilities.
2. **OpenTelemetry Spans (Option 2)**: Integrate OpenTelemetry SDKs, exporting spans to external tracing backends (like Jaeger or Honeycomb). High power, but adds heavy external dependencies.
3. **Structured Event Bus (Option 3)**: Implement an internal structured event broker emitting serialized JSON events (e.g. `PlanCreated`, `ToolFailed`).

## Decision
**Option 3: Structured Event Bus**. Friday Core will implement a centralized, lightweight event broker. All components (Orchestrator, Tools, Memory) will publish typed events, which are written to local JSON files and piped to the FastAPI websocket bridge.

## Consequences
* **Positive**: Allows real-time GUI HUD dashboards to display execution plans, active steps, and latency metrics via the websocket bridge with low overhead.
* **Negative**: Requires implementing a custom, thread-safe event publishing queue.

## Rejected Alternatives
* **Option 2 (OpenTelemetry)**: Rejected due to significant package bloat and the unnecessary complexity of maintaining external tracing endpoints for local desktop usage.

## Future Revisit Conditions
Revisit if Friday's deployment expands to multi-agent cloud coordination, which would require standard OpenTelemetry trace integrations.
